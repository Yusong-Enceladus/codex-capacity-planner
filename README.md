# Codex Capacity Planner

> 非 OpenAI 官方产品。本项目与 OpenAI 没有隶属或背书关系；Codex 是 OpenAI 的商标。

Codex Capacity Planner 是一个本地优先的 Codex 工作容量决策系统。它不只显示额度，而是把个人用量、自然/强制/升级/重置券刷新、多账号容量、未来工作负载和公开重置信号合并成同一份可解释建议。独立 macOS App 与 CodexBar 集成读取同一份 snapshot。

## 安装

从 [GitHub Releases](https://github.com/Yusong-Enceladus/codex-capacity-planner/releases) 下载
`Codex-Capacity-Planner-macOS.zip`，解压后把 App 移到“应用程序”。下载版使用 ad-hoc
签名，没有 Apple Developer ID 公证；首次打开若被系统拦截，请在 Finder 中按住
Control 点按应用并选择“打开”，或在“系统设置 → 隐私与安全性”中选择“仍要打开”。
当前下载版面向 Apple Silicon（arm64）Mac，并已内置运行 Monitor 所需的 Node.js，
用户无需另外安装 Node.js。Intel Mac 可从源码构建对应架构版本。

也可以从源码构建：

```sh
git clone https://github.com/Yusong-Enceladus/codex-capacity-planner.git
cd codex-capacity-planner
./CodexResetApp/build-app.sh
open "CodexResetApp/dist/Codex Capacity Planner.app"
```

源码构建需要 macOS 14 或更高版本、Xcode/Swift 和 Node.js 22。首次构建会下载固定版本
的 CodexBar 源码并应用仓库中的可审查补丁。

维护者可运行 `./scripts/package-release.sh` 生成 ad-hoc 签名的 zip 和
`SHA256SUMS.txt`；推送 `v*` 标签时，GitHub Actions 会以相同方式创建 Release。

项目以 MIT 许可证开放。`patches/codexbar/` 保存基于 MIT 许可的 CodexBar 0.49.3 修改；构建时从精确上游 commit 生成 `CodexBar-upstream/`，不把第三方完整源码重复提交到主仓。详见 [NOTICE](NOTICE)、[架构](docs/architecture.md)、[隐私](docs/privacy.md) 与 [安全策略](SECURITY.md)。

- `CodexBar-upstream/`：由 `scripts/bootstrap-codexbar.sh` 本地生成，不进入版本控制。

首次构建会自动生成固定版本的 CodexBar 工作树，也可手动执行：

```sh
./scripts/bootstrap-codexbar.sh
```

这个本机集成把四类事实合在一起：`codex-reset.com` 的全局预测与 Tibo 信号、CodexBar 的个人额度、按账号读取的 banked reset 库存、以及浏览器后台 Push。事件先拆成两条互不排斥的影响轴：`forcedResetEffect` 表示是否会被动刷新，`bankedGrantEffect` 表示是否发放一张可自行选择的券。同一公告可以同时具有两种影响；只发券的公告绝不会进入强制刷新红线。

它分别回答三个问题：

1. 全局是否已经宣布或正在预测一次重置？
2. 这次重置是否已经真正落到本机所见的个人额度？
3. 如果账号有可用券，在券到期前什么时候兑换最有价值？

两者不再混为一谈。全局公告出现后进入“等待你的额度到账”，只有周额度下降或自动刷新时间向后跳变，才标成“你的额度已刷新”。

## Banked reset 决策

券的到期时间不是独立的“临期模式”，而是同一个有限期决策的终点。系统每次额度、库存、负载或强制事件变化后，都会在 `现在…到期` 的候选节点上重新比较 `RedeemValue(now)` 与 `HoldValue(now)`；求值范围至少覆盖兑换后的一整个周周期，因此会计入“兑换后下一次周刷新推迟约 7 天”的成本。只给建议，不调用兑换接口，也不自动切换账号。

当前账面诊断使用：

```text
净额度边际 = 当前已用比例 − 当前周周期经过比例
```

- 周期刚刷新就把额度用完时，净边际接近 `+100%`，通常是最好的兑换节点。
- 周期快自然刷新但额度几乎没用时，净边际接近 `−100%`，兑换最亏。
- 正常匀速时净边际约为 `0`；因为兑换还会失去继续等待的选择权，默认保留。

净边际只是可解释的容量账，不是完整目标。最终求值还会加入未来工作负载分布、额度耗尽造成的工作中断、券的到期终点、可能先到来的免费强制刷新，以及另一个账号是否能临时承接工作。复杂策略只有在时间顺序留后历史中优于简单基准时才应提高置信度；历史不足时显示降级结果，不制造精确日期。临期会自然缩小未来可选节点并降低 `HoldValue`；系统必须提前形成高价值兑换节点并安排已有的真实工作，不能等到券即将过期才临时制造任务，也不能把券过期当作可接受的规划结果。

输出严格分成三条独立动作：`workAction`（保持/继续/加速/Standard/Fast）、`creditAction`（等待到账/保留/准备/兑换）和 `accountAction`（留在当前账号/考虑具名切换）。强制刷新临近时可以同时出现“加速当前额度”和“继续保留券”，两者不冲突。

当前 Codex 只有周额度时，`primary` 缺失被视为“短窗口未启用”，不是读取失败；全部计算、通知和迁移只使用存在的周窗口，不会默认构造 5 小时限制。如果将来短窗口恢复，它只作为额外约束加入，不取代周窗口。

库存按账号保存稳定的去敏 ID、状态与时间。可靠空库存明确表示 0 张；`null`/读取失败保留上次可靠状态。旧券与新券通过 ID 和 `grantedAt` 区分；券在到期前无额度刷新证据地消失会标成 `disappeared-unknown`，不会冒充已兑换。额度刷新因果按可验证证据归类：券库存消耗优先判为兑换；付费档位真实上升且额度窗口重建判为升级；发生在既定周期边界判为自然刷新；其余提前重建的完整额度窗口判为强制刷新。小幅刷新时间校准不再生成历史记录。

多账号是单账号决策的兼容层，不是另一套“本机调度器”。每个 Codex 账号保留独立额度、刷新历史、连续红线与行为模型；主卡片严格跟随这台 Mac 的当前默认 Codex 登录，而 CodexBar 正在查看的数据源单独标识。账号以可辨认的实际名称缩写展示，套餐显示 `5x / 20x`；1–3 个账号完整列出，更多账号折叠但继续独立计算。只有另一个具名账号会实质改变下一步行动时，才提示切到谁、还需使用多少，系统不会自动切号或合并不同账号的额度百分比。

月度续费日不再被当作额度刷新边界。同档续费、以及订阅到期短暂回到 Free 后恢复原档，继续沿用原周额度冷却；有效付费期内升到更高档套餐时预期立即刷新，但本机仍只在观察到额度下降或自动刷新时间跳变后重建该账号周期。

## 计算口径

红线维护的是一条独立于真实用量的连续轨迹。设 `R(t)` 为时刻 `t` 的“计划剩余额度”，`A` 为确定的自然刷新上界；从 `t` 前进到 `D` 时：

```text
自然剩余 = R(t) × (A − D) ÷ (A − t)
预测后剩余 = 自然剩余 × (1 − p)
D 时刻红线 = 100% − 预测后剩余
```

`R(t)` 只随时间、确定刷新上界和当时已知的重置风险连续下降；真实已用比例 `U(t)` 只与红线比较，绝不反向写回公式。因此实际白色进度可以位于红线左侧、蓝区内，也可以自然越过红线。

这个公式不需要人为设置 50% 门槛、固定 6 小时、固定剩 3%，也不存在每 24 小时重新建立目标的问题：

- `p = 0` 时严格沿自然刷新前匀速归零的基线；
- `p = 1` 时在明确截止点前把计划剩余额度降到零；
- `D → A` 时手动刷新目标自然收敛到自动刷新；
- 概率改变只改变此后的斜率，不会让“此刻目标”瞬间跳动，也不会拿实际用量重新锚定；
- 唯一重建整条轨迹的边界，是本机实际观察到额度刷新并进入新周期。

卡片在没有更近的 Tibo 或自然刷新边界时，默认用未来 24 小时作为蓝区和红线的共同预测观察窗，因为这是网站直接给出的最近校准概率。它只是看连续曲线的一扇窗，不是计划周期；Tibo 截止或确定刷新更近时，观察点自动改用那个边界。

证据优先级：

- Tibo 明确重置公告：`p = 100%`；有官方传播窗口就用原窗口，没有具体窗口就显示“立即”，不编造时限。
- 有期限的 Tibo 承诺：网站给出的承诺概率下限与同期限历史模型取较高值。
- 普通历史模型：24 小时内按 `P24` 的等风险曲线，24–48 小时按 `P24/P48`
  两个累计概率分段插值；48 小时以后不擅自外推新概率。
- 普通候选暗示：若网站未给它数值权重，只展示，不擅自提高概率。

## 个人行为预测与实时强度

接收器按账号读取 CodexBar 已有的本机周额度历史，直接预测“从现在到同一截止时间，自然使用还会增加多少额度”。额度变化和训练历史严格绑定到对应账号；Session 活跃度只能说明这台 Mac 的当前短期负载，无法可靠归属到每个账号，因此不会参与跨账号排序。匹配不到账号归属时不跨账号猜测，短时爆发也不会再乘以 24 小时。

- 基准模型：只看近期完整的同长度未来窗口；14、30、60、90 天回看长度由时间顺序回测选择。
- 当前周期模型：使用本周截至现在的日历进度，并用过去周期在相同进度后的实际残差校准。
- 相似状态模型：比较当前周期位置、近 1/6/24 小时增量和已用比例；找不到足够接近的历史时自动降权。
- 较早的时间窗口用于选配置和模型权重，随后一段从未参与调参的较新窗口专门留作验证；组合模型只有在这段留后验证上不差于简单基准才启用，否则自动退回基准。历史不足、数据过期或结构异常时不显示伪精确预测，只保留当前额度、红线目标和确定差额。
- 输出是自然使用的中心值、25%–75% 主要范围、自然达标概率和仍需额外安排的额度范围。进度条中红线是期望值目标，青蓝短线是自然预测中心，半透明青蓝带是主要范围。
- 文字判断和图表严格共用这三个数：红线在蓝区内（含边界）是“基本合适”；红线完全在蓝区右侧是“明显偏慢”；红线完全在蓝区左侧是“明显偏快”。
- 明显偏慢时建议续跑近期 session 或新增有价值任务，仍不足时再开启 Fast；基本合适时保持当前节奏；明显偏快时只建议从 Fast 切回 Standard，不要求减少已有任务。
- 另有独立的“未来 1 小时负载”层：使用当前 2 分钟及最近 15/60 分钟的主 session 与全部 Codex session 活跃度，在最近 14 天的一小时窗口中寻找 80 个相近状态，输出下一小时预计再用额度的 25%–75% 范围与中心值。
- 这层模型来自严格的时间顺序留后回测，只负责短期负载，不改变上方同一截止时点的蓝区、连续红线或主建议。预测每约 55 分钟最多记一条本机影子记录，一小时后用真实额度结算；跨额度刷新或数据缺口的记录直接丢弃。
- 15 分钟与 60 分钟额度读数继续只说明“刚才的使用强度”，保留在右侧详情中作诊断；它们不参与截止时预测或落后提醒。

接收器每分钟只读取一次已经在本机运行的 CodexBar bridge，并保留当前周期最多 6 小时的小型滚动样本，用来补齐历史文件尚未落盘的末端。这个本机读取不会重新开启 CodexBar 自带的耗尽预测，也不会增加 X 或网站请求。

## 可考虑续跑的 session

当自然预测明显偏慢，或 Tibo 已明确公告但个人额度尚未到账时，卡片会列出最多 5 个“可考虑续跑”的近期 Codex session：

- 每约 5 分钟只读 Codex 本机 SQLite 中的标题、项目路径、最近活动、置顶状态、Goal 状态与累计 token 计数；不会读取体积很大的 rollout 文件、消息预览或对话正文。
- 只看本额度周期内、未归档且不是 subagent 的 session；明确完成的 Goal 排除。
- 排序依次参考可继续的 Goal 状态、置顶、本机观察到的 token 增量和最近活动。首次建立基线前不会把旧的累计 token 冒充成实时增量。
- 主卡片只显示前两个标题，右侧展开显示完整候选、理由和时间。候选数据库偶发读取失败时沿用最近可靠列表并标成稍旧，不影响额度计算与重置提醒。
- 系统无法从这些元数据可靠判断任务是否真的完成，所以只给建议；用户自行决定是否打开对应任务，系统不会自动发消息或启动 session。

## 信息结构

CodexBar 与独立应用读取同一份 snapshot，只允许展示密度不同。主卡片始终先给当前建议；偏慢时直接列出前两个可续跑任务。展开区固定为三栏：`账户`、`为什么这样建议`、`重置`。使用速度、速度来源、短期负载、自然预测、目标差距、候选任务和数据可信度按因果顺序放在“为什么这样建议”；自然刷新、强制刷新、重置券、套餐升级、Tibo 原文和最近五次刷新统一放在“重置”，不再拆成公告、券和数据状态等平级入口。

## 数据与提醒链路

```text
codex-reset.com Web Push ──低延迟唤醒──┐
                                      ├─ 本机接收器 ─ 个人公式 ─ CodexBar / macOS 通知
Atom feed ────────────────可靠补漏────┤
预测与 feed API ──────────模型/详情───┘
CodexBar CLI (127.0.0.1:18764) ───────个人额度事实源
```

- Web Push 是低延迟通道。页面可以关闭；浏览器后台组件仍可接收。第一次真实事件发生前状态显示为“已注册、待验证”。
- Atom 每约 15 分钟补漏，预测与 feed API 每约 10 分钟校准，均加入轻微随机抖动。
- 平时绝不轮询 X。只有收到真实 Push、但网站 API/Atom 尚未同步时，才对 Tibo 的公开页面做一次性补查。
- “明确公告”采用失败关闭：事件必须同时具备 15–22 位 X status ID、与 ID 一致的 `x.com/twitter.com` 原帖 URL，以及 API / Atom / Push 单次核验这三类可信来源之一；测试夹具或结构残缺的数据不会进入状态机。
- 每次成功取得新 Feed 都会反向对账当前事件：`rejected / failed / expired` 立即撤销；只由站点 API 发现、随后从新 Feed 消失的事件在 15 分钟宽限后撤销；`confirmed / verified` 仍保留到本机额度实际到账。Provider 还会把 Feed 顶层 `active` 与同 ID 的事件状态合并，避免上游字段彼此矛盾时显示假公告。
- 个人额度每约 1 分钟读取本机缓存。这个读取仅发生在 `127.0.0.1`，不会访问 X 或额外调用网站。
- 一小时负载层每分钟读取极小的实时 Session 计数；最近 7 小时的聚合特征最多每 5 分钟重读一次，训练集最多每 30 分钟重建一次。计算在独立 Worker 中进行并设 30 秒硬超时；数据库或系统负载异常时，接收器继续使用上一份可靠预测并标为稍旧，不会阻塞额度刷新或通知，也不会增加任何网络请求。
- 本机接收器启动时会立即用持久化的最后可靠快照开放接口；额度、Session、短期模型和网站信号随后在后台补齐，重启不再等待整轮初始化。
- 接收器另外保留一条去身份化的最近可靠额度摘要。实时读取偶发超时时，卡片继续用它计算并按 CodexBar 原生规则显示“刚刚更新 / x 分钟前更新”；超过可用新鲜度后才停止建议。原始滚动样本不会进入状态 API。
- CodexBar 自身设为每分钟刷新，并在打开菜单时立即刷新，缩短原生卡片和 Codex Capacity Planner 卡片的显示延迟。
- Discord 继续作为独立的人类可见兜底，邮件继续作为已确认重置的外部兜底。
- 测试运行时默认只在内存中工作，只有生产入口显式注入状态写入器；因此测试夹具不可能再覆盖 `~/.config/codexbar` 的生产状态。
- Service Worker 的 capability token 遇到 403 会重新读取一次本机配置并重试；已有浏览器订阅会在接收器页面打开时自动补登记。若本机核验仍失败，通知只写“收到 Push、尚未核验”，不会冒充已确认重置。

## 通知规则

- 新明确公告：每个事件一次。Web Push 唤醒时由 Service Worker 显示，不再叠加一条 macOS 通知。
- Atom/API 补到一条 Push 漏掉的新公告：发送一次 macOS 通知。
- 本机观察到个人额度到账：再发送一次 macOS 通知。
- 普通预测：按一次新的 forecast revision 计算；只有界面所显示的整数“预测加速额度”比上一 revision 增加时才通知。首次启动只建立基线，不补发旧通知。
- 有期限承诺：每个承诺 ID 一次。
- 行为预测落后：只有红线完全位于自然预测蓝区右侧时通知一次，并给出“续跑 / 新增任务 / Fast”的顺序建议；回到蓝区内时通知已恢复，越到蓝区左侧时建议切回 Standard。预测上调与行为落后同时发生时合并成一条通知。

## 本机端口与进程

- `127.0.0.1:18764`：可选的 CodexBar CLI 数据源，只监听回环地址。
- `127.0.0.1:18765`：Codex Capacity Planner Monitor，提供脱敏的状态和共享 snapshot，并可把 `/usage` 反代到 18764。
- 独立 App 会启动或复用 18765 上已有的 Monitor；CodexBar provider 也读取同一个地址。
- 同一用户会话只应运行一个 Monitor。个人 LaunchAgent 配置和本机绝对路径不进入版本控制。

外部信号服务默认是 `https://codex-reset.com`。该网站是独立第三方服务，不由 Codex
Capacity Planner 项目或本仓库维护者运营。Monitor 可通过
`CODEX_RESET_SIGNAL_BASE_URL` 替换为兼容服务；CodexBar provider 可在同名设置中配置。
服务首次不可用时系统退回只基于本机自然刷新和个人用量的规划，不会让整个卡片失效。

## 隐私边界

个人使用率、自动刷新时间与计算结果只保存在本机。外部固定请求不携带个人额度、账号、邮箱或刷新时间。

Session 候选同样只在本机处理并通过 `127.0.0.1` 交给 CodexBar：对外不发送标题；本机状态接口也不包含 thread ID、完整路径、消息预览或对话正文，只保留展示所需的标题、项目目录名和派生排序信息。

一小时负载模型只读取额度百分比、事件时间、模型提供方、模型/思考强度元数据和去身份化的 Session 活跃计数。影子状态只保存预测值、实际额度增量与误差；不保存标题、thread ID、项目路径或对话内容。

启用 Push 时，浏览器生成的 Push endpoint 与语言会经本机接收器发送给 `codex-reset.com`。接收器不保存 endpoint 原文，只保存不可逆 SHA-256 摘要与注册时间；本机 capability token 不会发送到外部，也不会出现在日志或状态 API 中。
